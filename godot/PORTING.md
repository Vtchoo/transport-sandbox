# Godot port

Target: Godot 4.7.2 .NET, desktop first, with one metre per world unit. The original Vite game is retained as the behavior reference during migration. This folder is an in-progress native port, not yet a replacement for the browser game.

Open `project.godot` in the .NET editor and press F5 to run the project. Start game opens world setup. In the world preview, WASD pans, middle drag orbits, right drag pans, the wheel zooms, C toggles free camera, and Q/E changes free-camera height.

The project now requires the .NET editor and .NET 8 SDK or newer. The editor builds the C# assembly when running; for command-line tests, first run `dotnet build "godot/Transport Sandbox.csproj"` from the repository root. The solution uses Godot's Debug, ExportDebug and ExportRelease configurations.

## Present

- The ten catalog vehicles, exported for every supported gauge as GLB, including distance-driven steam running-gear animation tracks. Metadata preserves mass, power, tractive effort, dimensions, gauge availability and exhaust outlets. Browser canvas-generated lettering and logos are embedded at their original resolution, with unlit alpha materials and the same depth-write behavior in normal and placement-preview rendering.
- C# terrain generator v1, with numerical and mesh fixtures generated from the original implementation. Immutable sampling settings and per-job buffers allow parallel chunk generation without changing the seeded heightfield.
- Gauge-aware signed-endpoint track graph: Bezier handles, parallel groups, split/merge, station grouping and junction restrictions.
- Worker-based directed routing with shared destination fields and a bounded cache/queue, connected to train station/waypoint orders. Unchanged connected networks retain their fields and jobs after edits; unaffected installed journeys continue during background replanning.

The startup scene provides the station/train menu, recommended/advanced world setup, streamed terrain with LOD, trees, contours and overlook/free camera controls. Track rendering uses the original swept rail, ballast and platform profiles, with instanced sleepers. Track/station editing, train building/placement and realistic/HO train movement are available. Do not treat the project as feature complete.

## Saved worlds

Press **Esc** when no tool/window consumes it, or use the HUD **Menu** button, to open the centered pause menu: **Resume**, **Save game**, **Quit to menu**, **Quit game**. Opening it pauses the scene tree (including trains, camera, terrain streaming and timers); the menu itself continues processing. Resume, Escape, or its close button restores gameplay. Saving stays paused and keeps the menu open. Both quit actions wait for a fresh save and clear the pause state before changing scenes/exiting; failed saves keep the session available. Conflicting menu actions are disabled during writes. Existing Escape behavior for closing tool windows, canceling construction, or releasing the free camera takes precedence.

New game includes a world name. Saves live under Godot's `user://worlds/<slug>/` (`%APPDATA%/Godot/app_userdata/Transport Sandbox/worlds` on a standard Windows install). Names are converted to safe ASCII slugs; collisions append `_` repeatedly. Use **Load game** on the menu, **Save / F5** in gameplay, or the five-minute autosave. Returning to the menu and normal window closing wait for a fresh save; a save failure keeps the session open. Forced process termination cannot trigger save-on-exit.

`world.json.gz` is the versioned complete simulation snapshot: absolute double coordinates, track handles and gauge, stable ID allocators, parallel groups, station membership/platform sides, directional signal types, composed and draft trains, vehicle facing, parked poses, running/speed/direction, all order types, active order/timed wait, seeded itinerary history, wandering service progress, signal reservations and camera pose. All simulation entities load together and train movement has no dependency on visible terrain chunks. Derived destination fields rebuild on load. Snapshots are captured on the main thread and compressed/written on a worker, with atomic replacement and `world.previous.json.gz` retained as the previous successful save.

Only chunk content is streamed from `regions/r.<x>.<z>.tsregion`. Each region covers 32?32 of the existing 512 m chunks, using floor division at negative coordinates. Records hold compressed resolved vertex/normal/color/index arrays for each generated LOD plus natural vegetation data. The first request for a previously unseen LOD still generates it; subsequent requests and cold restarts decode its saved result. GPU upload and tree instance preparation still happen on load. The existing bounded mesh/tree memory caches remain; disk indices retain at most four regions. No region terrain data is required for train routing or movement.

Region I/O runs on terrain workers. SHA-256 settings/algorithm and local earthwork signatures reject stale records; distant terrain remains reusable after local track edits. Loading waits for the initial earthworks snapshot before requesting terrain. Checksums reject damaged payloads, incomplete trailing writes are ignored/truncated at the next append, and superseded records are compacted once a region exceeds 64 MiB and twice its live size. Region files are a custom format inspired by Minecraft's organization, not compatible with Minecraft's Anvil format. Future terrain/vegetation algorithm changes must bump the identity in `TerrainRegionStore`.

Run `tests/runner.tscn -- --suite=saves` headlessly for slug collisions, negative regions, interrupted appends, bounded indices, generator/earthwork invalidation, exact mesh/vegetation cold reads with zero regeneration, composed trains/orders/reservations and floating origins, saved ID counters, timed waits, autosaves, menu loading, and train movement with no terrain world. This suite also runs under `--suite=all`.

## Camera and floating origin

`CameraRig.cs` ports `src/camera.ts` numerically: WASD/arrows, Q/E overlook rotation, normalized 3D free movement with E/Space/Q, mode-specific Shift speed, exponential wheel zoom/free speed, pitch limits, terrain-ray mode transitions and follow cancellation. Movement waits for loaded terrain; camera clearance uses the rendered terrain triangle heights. `WorldCamera.cs` maps native mouse wheel notches to 100 CSS pixels, handles left/right pan and middle orbit, captures the mouse for free look, releases it on Escape/modal UI/focus loss, and uses right-drag free look while constructing. Following preserves the current camera mode.

`node scripts/export-godot-camera-fixtures.mjs` captures camera action sequences from the browser, including negative and billion-metre positions. Core checks compare positions, targets, angles, limits, speeds and follow state. Native checks cover input blocking/capture, double graph storage, grid anchoring, train poses, terrain queries and mesh/job preservation across origin changes. Mouse capture assertions require a graphical display server; headless tests cover the remaining behavior.

## World surface rendering

Gameplay terrain and water now use the browser's hemisphere/directional illumination, GGX direct specular, ACES exposure (1.05), sRGB transfer and exponential-squared distance fog (density 0.00034). Terrain retains the original two-frequency ground grain and antialiased contour overlay. Chunk meshes store sRGB vertex colors; the shader decodes these before interpolation and lighting. GPU fixtures use this same packed color encoding and cover meadow, shore, rock, snow and cut/fill palettes, preventing a false pass from directly supplied linear test colors. The shader receives the floating origin after rebasing so texture coordinates remain anchored to absolute world axes. This changes surface shading only; mesh generation, cuts/fills, caches and worker scheduling retain their existing behavior.

Water retains the 32,000 m square, sea-level height, camera-centered placement, original #437c85 color, 0.25 metalness, 0.28 roughness, 0.88 opacity and depth writes. The gameplay sky ports the original horizon/zenith gradient, sun glow and disk through a native sky shader. Its output adapts to Compatibility's sRGB sky input; see [Godot's sky rendering implementation](https://github.com/godotengine/godot/blob/master/drivers/gles3/shaders/sky.glsl). Godot directional shadows are intentionally retained: terrain and water use a custom `light()` pass to attenuate sunlight with the native shadow map, while preserving hemisphere light, exposure and fog. Gameplay uses four cascades over 2,500 m, aligned with the original sun direction. The menu's existing environment is unchanged.

`node scripts/export-godot-world-visual-fixtures.mjs` records 17 GPU reference pixels from the actual browser terrain/water materials and sky shader. It uses Chrome through the same private export page as the vehicle exporter. After building, run `godot --path godot tests/runner.tscn -- --suite=visuals` with a graphical display server. Checks allow a maximum difference of 3/255 per RGB channel across ground positions, near/far fog, water blending and sky/sun directions, and verify ground grain after origin shifts. An additional real box-caster test verifies shadow reception on terrain/water and restored brightness after the caster is hidden. These passed on the RX 6600 Compatibility renderer. The `all` suite includes these checks when graphical and skips pixel readback when headless; startup integration checks water dimensions, sea level and origin propagation in either mode.

This is surface-rendering parity, not a complete scene match. Trees, track/station materials and vehicles still use native material lighting and shadows; their fog, tone mapping and hemisphere response remain to be ported. Forward+/Mobile pixel output has not been verified. The original browser remains the appearance reference.

The track editor's `TrackNodeHoverMenu` now follows the browser's screen projection: hover within 100 px of a node to select its tangent side, with continuation 65 px along that side, delete 32 px beside it, and parallel-node controls on the projected lateral axis. GPU captures were reviewed at 1280x800 and 700x800. `compare-godot-menu.mjs` accepts `game`, `build`, `view` and `settings` states in addition to the menu/setup states. World surface rendering is described above; lighting and fog on native object materials remain unfinished.

The track tools include the original world grid selector (Off, 1, 5, 10, 25 metres). G toggles snapping and restores the last nonzero spacing. Snap rounding matches JavaScript even at negative half-cell boundaries. Existing-node placement and Shift's outgoing straight alignment take priority.

Selected parallel groups expose purple lateral spacing handles about 25 screen pixels outside their nodes. ## Train building, placement and movement

`TrainBuilder`, `TrainPlacement`, `TrainEditor` and `TrainWindows` port the browser building/placement workflow. A catalog click appends at the rear of the frontmost expanded train window only when its Edit train tab is open; otherwise it creates a new train and opens that editor. The catalog owns no train selection and filters by the common vehicle gauges, plus the placed train's actual track gauge. It retains the original per-model SVG thumbnails and a hovering/focused vehicle's rotating 3D preview.

Each train has Viewport/Edit train tabs, horizontal front-to-rear cards, insertion gaps, drag-and-drop reorder/transfers, flip/remove controls, trash drop, Add vehicles, Place train, Reverse preview (R), and stopped-only pickup. Clicking a placed vehicle opens its viewport. The viewport and Follow train focus on the first vehicle; pan input stops following. The viewport play/pause command starts a placed powered train or applies service braking. Speed is shown in km/h.

Placement follows arc distance across compatible opposite-side connections, rejects ambiguous junctions, insufficient track, overly tight rigid sections and overlap with other trains, and shows translucent original models with valid/invalid tint and a cursor hint. R reverses the preview, Escape cancels without changing construction, hovering a stopped train's front/rear coupler previews attachment, and committing merges the incoming consist into it. Leading couplers snap within 5 m to station-run ends on their own track, including runs spanning split segments. Vehicle bodies, bogies, and the permanently coupled Rio Grande engine/tender follow independent source poses at real dimensions.

Stopped consists remain on rails when edited, preserving the first surviving original car's location. An edit that runs out of free track or exceeds the curve clearance lifts the train for repositioning; other invalid edits roll back. Moving/started trains reject edits and pickup with a pointer warning. Editing/removing supporting rails updates the train or marks it unsupported without teleporting it.

Placed models use merged material surfaces for reusable body/bogie templates and `MultiMesh` instances grouped in 512 m cells. Picking still tests the original model triangles. Diesel/steam exhaust responds to delivered traction with the browser emission rates, smoothing and particle parameters. Steam running gear uses the baked distance-driven animation; animated parts have independent instancing transforms. Draft/catalog viewports use private worlds; placed-train views share the live game world and update at the browser's viewport intervals.

`TrainMovement` and `TrainRoute` port bounded 1/60 s stepping, seeded opposite-side junction choices, persistent per-visit itineraries, mass-weighted grade, realistic/HO force integration, curve braking over the entire consist and approach, occupied-track braking and overlap rejection, and automatic reversal before dead ends and wrong-way signals. Trains brake to a full stop two metres before a wrong-way signal before reversing; a red signal alone does not cause reversal. The world seed and physics selection feed the simulation. HO now uses OpenLoco-derived power/weight acceleration, speed-squared drag, speed-dependent braking and an 8 km/h hill-speed floor, with finite hill starts. It uses uncompressed catalog speed ratings. Safety targets override the floor and can stop the train completely; continuous spline grades and radius limits remain supported. See `docs/train-physics.md` for the source formulas and adaptations. Stopped edits and transaction rollback retain the occupied itinerary. Missing or invalid supporting track stops the affected train at its last valid pose. MultiMesh batches update their transforms in place, rebuilding only changed cell/count membership. Node-mounted normal, chain and path signals control movement through blocks and reservations; bounded local detours can select clear passing lines before a blocked signal.

The track builder now has an icon-only Signals tab with Normal, Chain and Path selectors and build/replace/remove actions. Signals occupy a node's two directional slots. Direction selection follows the local OpenLoco source: compare the cursor's screen-space Manhattan distance to points ahead of and behind the node, then face the approaching train. Pole placement remains on that train's right. The Single/Both directions selector places or removes either one slot or both together; placing one direction prohibits the opposite direction until its opposing signal is added. They follow node position/direction and floating-origin rebasing; deleting a node removes its signals. Large direction arrows sit over the track centerline while the Signals tab is active, including on already placed signals. The adapted selection code is attributed under `third-party/OpenLoco-LICENSE.txt`. Normal heads are rectangular, chain heads diamond-shaped, and path heads have a yellow identification bar. Signals cannot be placed freely on segments: split the segment first.

Normal signals exclusively reserve the next physical block. Chain signals atomically reserve whole blocks through subsequent chain/path controls to a normal exit and its receiving block. Path signals reserve only the selected itinerary through their region, permitting simultaneous non-conflicting routes, and also reserve a clear receiving block after a normal exit. Receiving blocks must be clear, with no minimum length relative to the train. Players are responsible for leaving enough space beyond junctions; a train may span several occupied blocks. Missing normal exits and cyclic signal dependencies fail closed. Red controls brake the leading coupler two metres before the node. Leases remain until the rear clears, and pending leases are dropped after itinerary/direction changes or removal of the train. Stopped trains participate in occupancy. Existing close-range collision braking remains as a fallback. This implementation borrows the central block/exit/reservation behavior from [Factorio chain signals](https://wiki.factorio.com/Rail_chain_signal) and [Satisfactory path signals](https://satisfactory.wiki.gg/wiki/Path_Signal); it is not a reproduction of their entire signal UI or every placement restriction.

`RailInterlocking` builds physical gauge-compatible blocks at signalled boundaries. Main-thread occupancy uses the train's complete itinerary footprint; reservations are granted atomically and never alter cached destination costs. Shared junction nodes and sampled geometric crossings conflict, including disconnected graph crossings, while sufficiently separated overpasses and parallel paths can proceed concurrently. Control-point bounds reject distant pairs before arc-table construction; crossing tests use roughly four-metre chords (capped at 4,096 per segment), with a cached clearance envelope. Idle aspects refresh at five Hz and approaching trains evaluate permissions every physics step. Geometry/topology/signal edits rebuild the block map and reservations from current occupancy. This interlocking is synchronous; large-network traffic performance, fairness/deadlock recovery and block overlays remain future work. Signals at junctions separate the two approach halves while keeping same-side branches in the same physical block, so a normal signal cannot bypass whole-block occupancy by selecting a sibling branch. Chain indicators can show blue for a mixture of clear/blocked exits; path indicators stay red until a request succeeds.

Chain aspect discovery follows directed, gauge-compatible connections through every unsignalled node and junction to the next actual signal. Wrong-way signals and dead ends are blocked exits; downstream mixed chain aspects propagate blue. Signal-to-signal topology is cached until a network edit. Train admission separately follows its chosen itinerary and atomically reserves through chain/path signals to a normal exit and a clear receiving block, regardless of its length. A green alternative exit never authorizes the train to use its blocked chosen exit. `--suite=signals` covers junctions beyond several plain nodes, mixed exits, chained exits, wrong-way exits, and pending-reservation replacement.

`ChainStationChecks` adds twelve headless movement regressions for one-to-two turnouts and two-to-two crossover station throats at 5 m track spacing. Every approach/platform combination runs an F7 with two coaches through unsignalled intermediate nodes and junctions, with the two normal exit signals either before or after the platforms. Tests verify initially green exits/entries, chain passage, exact platform-end arrival, timed-wait execution, and no reversal or detour. Run `--suite=chain-stations` alone, or use `--suite=signals` / `--suite=all`.

Click a signal's pole/head to open its directional signal inspector (outside active signal placement). The focused, expanded signal window draws its scope on the world; changing focus, closing, collapsing, minimizing, opening a modal, or pausing hides the overlay. Normal signals show the following physical block; chains traverse unsignalled nodes and downstream chains/path signals through normal exits and their receiving blocks. These queries use the interlocking topology without acquiring reservations or changing aspects.

Path inspectors show structural conflicts: all routes from the selected entry are blue, routes from other entries sharing/crossing any selected route are red, and independent routes remain blue. Shared sections retain a narrow blue center on a red border. This is independent of live train occupancy. Signed connections, signal boundaries, gauge, junction conflicts, crossing clearance and overpass separation use the reservation rules. Nearby disconnected geometric crossings are included. Path enumeration is bounded to 512 routes, 8,192 visited states, 128 edges per route and 100,000 conflict comparisons; the window explicitly reports truncation/conservative coloring. Geometry is rebuilt only on selection/topology changes; absolute stroke coordinates survive rebasing. `--suite=signals` / `--suite=all` cover picking, focus lifecycle, plain-node/chain scopes, multiple selected routes, shared rails, disjoint paths, geometric crossings and overpasses.

`RailDetourSearch` performs a forward local Dijkstra search when live signal permission blocks a train. It rejoins a future occurrence of the existing itinerary before the active order, preserving gauge, signed connections, one-way signals, station-entry penalties, occupied history and the original suffix. Searches cover at most 2,000 m, 128 original legs, 256 expanded states and four candidate validations; a detour may add at most 500 m. At most two attempts run per `AdvanceMovement` call (normally one frame), and each train retries after 2-2.78 simulated seconds. These bounds cap local work without invalidating shared destination fields. Pure reservation previews leave aspects and leases unchanged. Entered reservations lock their route choices; pending leases are replaced and reacquired through the normal interlocking. No safe alternative means the train keeps waiting. Detours never introduce reversals and currently apply to signal-blocked routes, not unsignalled collision waiting or an itinerary already planning a reversal. Wandering trains rescan for station service after a successful splice.

`--suite=signals` includes local detour tests: an F7 passes a stopped train and reaches the exact station edge without another destination-field search; reordered occurrence indices and reverse travel retain the original suffix. Other checks cover occupied normal blocks, conflicting reservations, entered leases, one-way restrictions, next-order preservation and unlisted station penalties. A small CPU diagnostic runs 100 searches with 102 live train footprints; its printed timing excludes rendering and does not represent full-network simulation performance.

Station orders additionally allow a bounded live search to any reachable platform end belonging to the same station, without requiring a rejoin of the original approach. This keeps the current order and exact end stop, preserves occupied history and entered reservations, and uses the same work/cooldown bounds as other detours. Signal boundaries separate opposite halves even at branching nodes; an occupied platform beyond its entrance signal does not also occupy the throat. Trains at rest with their running command off release pending reservations, and order holds do not acquire future leases. Occupied reservations remain protected until the rear clears.

`StationTrafficChecks` runs in the signal/all suites and checks alternative platforms, occupied platforms/throats, one-way restrictions, reverse-running consists and entered reservation locks. To replay the specific four-train reported layout, copy its save directory and run `--suite=station-traffic-save --save=<copied-directory>`; this diagnostic only reads it. It verifies both approaching trains stop at the empty platform end and execute their timed waits in succession. It does not write the player's world.

New parallel tracks default to 5 m center-to-center at 1,435 mm gauge, adjusted by the difference in gauge in metres. Existing parallel offsets are unchanged. Signal offsets adjust by half that gauge difference, leaving one metre between opposing signal pole centers on newly parallel tracks. The previous wider platform-specific spacing is preserved. `--suite=signals` checks placement, both directional slots, replacement/removal, gauge clearance, one-way destination routing, normal versus chain behavior, atomic reservations, rear clearance, path concurrency, crossing/overpass conflicts, long trains entering short clear exit blocks, node deletion and floating-origin behavior. It also drives a real train to a red signal and verifies departure after the obstruction is removed without a new destination search. The full suite includes these checks.

The train window's Routes tab supports station destinations (click a platform/track in the world or use its Stations list), pass-through waypoints selected from existing nodes, and timed waits in seconds/minutes/hours. Full-load/item selection remains disabled until cargo exists. Orders repeat, can be dragged to reorder or to the trash, and Copy/Paste appends independent orders to another train. Station arrivals align the leading coupler with the exact platform run end, including dead-end platforms. Signal and collision limits still take priority; signals retain a two-metre stopping clearance. Reversal is allowed at dead ends and wrong-way signals; unreachable or deleted destinations stop the train safely and replan after network edits. Trains with no orders keep wandering. Pausing a train pauses its wait countdown. The frontmost train's open Routes tab highlights all its station segments and waypoint nodes, labels them with order numbers, and uses gold for the current destination and cyan for the others. Highlights disappear on tab changes, window collapse/close or modal dialogs, and survive origin rebasing. Run `--suite=orders` for focused schedule, routing, UI and highlighting checks; `--hover=train-orders` supplies a visual capture fixture.

Scheduled trains make automatic station stops only for their active station destination; they pass through unlisted stations even when the only valid path crosses one. Explicit Wait orders, manual stopping and safety/obstruction braking still apply wherever the train is. With an empty order list, `TrainWandering` follows the seeded random itinerary and stops once per encountered station run, two metres before its far end. It stays while station loading/unloading work remains and departs once idle, without a fixed dwell timer. `TrainEditor.ServiceStation` is the cargo-service hook: return true while work remains, false when idle. Cargo handling is not implemented yet, so an absent hook means nothing to do; the train stops and continues on the following simulation step. Consecutive segments and visual sides do not multiply stops. Manually stopping the train pauses station work; a return visit in the opposite direction stops again. Adding orders cancels the wandering stop state immediately. Wander discovery uses the existing itinerary within braking lookahead and scans at most every 0.25 simulated seconds when no station target is cached. It does not enqueue pathfinding jobs or create synthetic orders. Dead-end platforms finish station work before reversing. `--suite=orders` covers scheduled pass-through, wandering arrivals/departures, busy/idle service, paused station work, return visits, route changes and dead-end platforms.

When an order is unreachable, the train service-brakes and remains stopped with its order unchanged. Both Routes and viewport status show `Can't find a route to the destination: Station/Waypoint N`; the pointer warning appears once per failed journey rather than every simulation tick. Failed continuation after a pass-through waypoint is detected before taking a random exit and identifies the unreachable following order. Track/order edits invalidate the cached failure and retry automatically. The train never falls back to wandering while orders remain. `--suite=orders` verifies missing destinations, disconnected stations/waypoints, persistent stopped position, one-shot warnings, both status displays, waypoint continuation failure and recovery after reconnection.

`node scripts/export-godot-movement-fixtures.mjs` records browser junction itineraries, clearance, curvature and realistic/HO trajectory checkpoints. The train suite verifies these fixtures, plus native play/pause, reverse movement, service braking, stopped edits, stable instance nodes, collision waiting and unpowered start rejection.

Refresh thumbnails and articulated-section metadata with `node scripts/export-godot-train-metadata.mjs` (also called by the full asset exporter). `node scripts/export-godot-train-fixtures.mjs` captures browser placement/walking/station/rigid-section fixtures. `--suite=train` checks those numerical fixtures and native catalog routing, construction, transfers, placement, attachment, edits, collision rejection, gauge filtering, station snapping and stopped-only pickup. Native captures support `--hover=train-edit`, `train-preview` and `train-viewport` with `--state=game`. Headless train tests drain queued node deletion and managed finalizers before quitting to release temporary preview/mesh resources while Godot's C# runtime is alive.

## Scalability design

`TerrainMeshCache.cs` retains inactive uploaded meshes and natural-tree records by chunk, LOD and earthwork revision, bounded to an estimated 128 MiB and 256 entries. Active chunks do not count toward that budget. Returning to a cached LOD or unloaded chunk mounts the existing mesh without worker generation or re-uploading geometry. Least recently used entries are evicted and their mesh references disposed. Entries too large for the budget are not retained. Train routing operates on directed track segments, not terrain navigation meshes. The state includes the direction of arrival, so two branches on the same node side cannot become an illegal U-turn. Route requests happen on departure, destination changes and invalidation, rather than each simulation tick. Static destination routing remains independent of live occupancy; the interlocking controls permission to move. Signal direction masks participate in immutable graph snapshots, while red/green changes do not invalidate destination fields.

`TrainRoute` keeps an immutable compact plan separately from its materialized traversal history. The roughly 3 km trim limit applies to that history, so distant planned junctions are never replaced by random choices. Copies/rollback share the immutable plan; replanning replaces only future travel beyond the leading coupler, preserving occupied junctions, and empty-order wandering clears the old plan. Arrival checks the actual leading-coupler route visit/position before completing an order; an exhausted distance counter at the wrong location stops and replans.

Keep logical train state separate from rendering. Use compact arrays for position along a route, speed, mass and traction; evaluate track-aligned movement analytically instead of using wheel rigid bodies. Use a fixed simulation timestep and interpolate visible vehicles. Distant trains remain part of the traffic simulation, but need no bogie transforms, running-gear animation or exhaust particles.

`RailRoutingGraph` builds an immutable, densely indexed directed graph with node adjacency in linear graph size (plus connection enumeration). `RailPathfinder` shares reverse Dijkstra destination fields among trains with the same destination and station order set. Search priority is lexicographic: fewest reversals (at dead ends or wrong-way signals), then arc distance plus station penalties. Any route without reversing wins over every reversing alternative, however long. Entering a station absent from the train's entire orders list adds 10,000 equivalent metres of cost (`RailRoutingPolicy.UnorderedStationPenalty`). This is a finite penalty, not a prohibition; it applies once per contiguous station entry rather than per platform side or split segment. Stations anywhere in the orders, including future stops, are exempt, as is the current station destination. Starting inside a station does not add another entry charge. Physical journey/braking distances exclude penalties. Immutable, canonical station sets keep worker caches separate for different schedules and share results for equivalent sets; order edits automatically refresh the policy and invalidate the affected train's journey. Partial first/last edges, gauge restrictions, station run ends, pass-through waypoints and occupied train itineraries retain their original behavior. `RailRouter` remains the small synchronous test reference, not the live runtime router.

Graph construction and searches run on managed workers (default at most two), with a maximum of 128 queued distinct destinations. Callers retry rejected requests on later frames instead of allocating unbounded tasks. Waypoint exit dependencies take queue priority. Destination fields use a least-recently-used cache capped at 64 entries and a 64 MiB array-data budget; one field larger than that budget is retained singly so very large graphs still work. Graph storage and active workers' scratch arrays are additional. Main-thread snapshot copying uses a soft 2 ms budget per frame after the edge-reference array is captured; initial array allocation/capture is not budgeted. Workers reuse exact arc lengths for unchanged spline controls after edits. Shutdown cancels without blocking the scene thread. No worker reads Godot nodes/resources or mutates the live network.

`RailRoutingSnapshot` partitions physical connectivity by node and gauge. Unchanged components reuse their exact immutable graph instances, cached destination fields and in-flight searches. Geometry, connection-side, gauge, station, merge and split changes rebuild only affected components; unrelated visual/no-op notifications retain all graphs. A replacement snapshot still scans the full network on a worker. New requests wait for publication, while installed journeys continue. Stale builds are canceled, and publication cancels/discards searches only for replaced components. Build/search workers share the same concurrency limit.

Journeys retain planned-edge dependencies and a component version. Edits elsewhere in a changed component trigger background replanning without braking. Edits touching a planned edge or its adjacent connection require a replacement before proceeding. This is conservative: dependencies include the full installed journey, including already traversed edges and waypoint continuation. Change history is bounded to 32 publications / 100,000 edge IDs; older journeys replan conservatively. Missing future track blocks lookahead and triggers braking/replanning without falsely marking the train unsupported. Missing occupied track still stops the train immediately. Unreachable journeys retry after relevant component changes without repeating the same warning. Wandering station service survives unrelated notifications. See [invalidation checks and measurements](../docs/performance/rail-routing-invalidation-2026-11-19.md).

Searches compress uninterrupted corridors by propagating exact costs/continuations directly through states with a unique predecessor and successor. They stop queue compression at branches, merges, station boundaries, destination states and reversals. Arbitrary waypoints inside corridors and closed loops remain supported; dense field arrays and fully expanded paths retain all original segments. This reduces priority-queue work without approximating lengths or penalties. `Search(..., compressCorridors: false)` remains available as the A/B reference.

Run `--suite=routing` for directed-path parity, corridor comparisons, forward-route preference, component invalidation, bounded scheduling, shared requests and cache eviction; `--suite=orders` also checks long-distance train/UI integration and movement across edits. `--suite=routing-performance` measures 500 requests on a 100,800-segment grid with shared and unique destinations, cold/warm latency and post-edit length reuse. `--suite=corridor-performance` compares compressed/uncompressed searches on an identical 99,900-segment corridor-heavy network. `--suite=invalidation-performance` compares a localized edit with a full cache reset across 20 networks / 100,000 segments. These measure pathfinding only, not 500 fully simulated/rendered trains. See the [original routing report](../docs/performance/rail-routing-2026-11-18.md) and [corridor comparison](../docs/performance/rail-routing-corridors-2026-11-19.md). Regional hierarchy, finer graph updates within a connected component and start-specific searches remain possible optimizations for large bursts of unique destinations.

Use spatially partitioned MultiMeshes for sleepers, trees, repeated train bodies and bogies. Bucket by geometry/material/gauge, world cell and LOD. A world-wide MultiMesh prevents useful culling because all its instances share visibility. Near vehicles may use individually animated detail; distant instances should use simpler geometry. Limit shadows and smoke by distance as well as polygon counts.

`WorldSpace` retains the absolute origin in double precision and rebases rendering on the camera's 512 m chunk. Track nodes and parallel origins retain absolute `TrackVector` coordinates; their `Position`/`Origin` properties expose local Godot coordinates for interaction. Train route parameters and arc tables retain double precision; world controls feed earthwork snapshots without converting through floats. Chunk meshes, local track meshes and cached terrain survive rebasing. Shared train/station viewports, previews, smoke, grid snapping and camera picking follow the same origin. Extremely long individual segments and remote secondary viewports remain subject to Godot's float transform precision; use ordinary segment lengths rather than one world-spanning spline.
